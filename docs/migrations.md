# Schema and migrations

There are two ways to use this ORM, and the difference between them is one
question: who decides what the schema is.

| | `mode: database` | `mode: managed` |
|---|---|---|
| source of truth | PostgreSQL | the Go declarations |
| schema changes come from | your existing migration tool, or hand-written SQL | `orm makemigrations` |
| `orm check` proves | the structs match the schema | that, plus models ↔ migrations ↔ database |
| `orm generate` | emits the typed API | the same, after checking the three states agree |

Both end in the same place: a proven mapping and generated code. Neither is a
lesser mode, and a project can move from the first to the second without
recreating anything — see [Adopting an existing database](#adopting-an-existing-database).

The workflow is state-based, inspired by Django's `makemigrations` / `migrate`
ergonomics. It is not Django-compatible and does not try to be: the schema model
here is PostgreSQL's own, and everything below that a portable abstraction would
have to drop — partial indexes, `INCLUDE`, `CONCURRENTLY`, `NOT VALID`, enums,
identity and generated columns — is a first-class part of it.

---

## Choosing a mode

```yaml
version: 1

schema:
  mode: managed          # or database, which is the default
  dsn: ${DATABASE_URL}
  search_path:
    - public

migrations:
  dir: migrations

packages:
  - path: ./internal/domain
    output: same
```

The mode is never inferred. A project with migration files is not thereby a
managed project, and one without them is not thereby database-first — the two
have different sources of truth, and guessing which one you meant is how a tool
ends up proposing to drop a table your other migration system created.

`orm init --mode managed` writes a starting configuration for the second column.

## Declaring a schema

In managed mode the declarations describe the schema. They describe only what a
Go type cannot say; everything derivable from the field is still derived.

### Field tags

```go
//orm:table users
type User struct {
	ID        int64     `orm:"pk,identity"`
	Email     string    `orm:"unique"`
	Nickname  *string
	Active    bool      `orm:"default:true"`
	CreatedAt time.Time `orm:"default:now()"`
	Slug      string    `orm:"generated:lower(email)"`
	Handle    string    `orm:"pgtype:citext"`
}
```

| tag | means |
|---|---|
| `pk` | part of the primary key, in field order |
| `identity` / `identity:always` | `GENERATED BY DEFAULT` / `ALWAYS AS IDENTITY` |
| `unique` | a `UNIQUE` constraint on this column |
| `default:<sql>` | the `DEFAULT` expression |
| `generated:<sql>` | `GENERATED ALWAYS AS (<sql>) STORED` |
| `pgtype:<type>` | the PostgreSQL type, when the Go type does not decide it |

The column name comes from the field name, the type from the Go type, and
nullability from whether the type can hold NULL — `*string` is a nullable
column, `string` is `NOT NULL`. None of that is repeated in a tag, because a
second place to say it is a second place to get it wrong.

**A default is SQL, not a Go value.** `default:true` is the expression
PostgreSQL stores. A Go zero value is not a default and never becomes one.

### Struct-level declarations

```go
//orm:table posts
//orm:index posts_feed_idx (AuthorID, CreatedAt desc) include (Title) where "status = 'published'"
//orm:unique posts_author_slug_key (AuthorID, Slug)
//orm:check posts_title_not_blank "title <> ''"
type Post struct { ... }
```

Index options: `unique`, `concurrently`, `using <method>`, `include (...)`,
`where "<expr>"`. Key options: `asc`, `desc`, `nulls first`, `nulls last`, and an
operator class. An expression key is written in quotes.

A unique *index* and a UNIQUE *constraint* are different objects, and the
declaration you write decides which you get: `//orm:index ... unique` is an
index, `//orm:unique ...` and the `unique` field tag are constraints. Only a
constraint can be a foreign key's target; only an index can be partial or over
an expression. Each is described in exactly one place, so `orm inspect` shows a
unique index among the indexes and never also among the constraints.

Enums and extensions are declared on the type that uses them:

```go
//orm:enum public.post_status (draft, published, archived)
type PostStatus string

const (
	PostDraft     PostStatus = "draft"
	PostPublished PostStatus = "published"
	PostArchived  PostStatus = "archived"
)
```

```go
//orm:extension citext
```

Declarations name **Go fields**, not column names. That is what lets a brand-new
project describe its schema, create it, and only then generate the code that
reads it — the declarations do not depend on anything generated.

### Foreign keys

A relation and a foreign key are one fact. The side that carries the constraint
is the side whose entity declares the key columns:

```go
type Post struct {
	AuthorID int64
	Author   orm.One[User] `orm:"side:local"`   // posts.author_id -> users.id
}

type User struct {
	Posts orm.Many[Post]                        // the same constraint, seen from the other side
}
```

The constraint is named the way PostgreSQL names one: `posts_author_id_fkey`.

### Precedence

Field tags establish; struct declarations enrich; conflicts are errors, never
silent overrides. A duplicate constraint name, a column declared twice, an
`INCLUDE` column that is also a key, identity with a default, and a declared
foreign key that contradicts a relation are all refused, with every problem
listed rather than the first.

## `orm makemigrations`

```
load the migration graph
        ↓
reconstruct the state the migrations describe   (M)
        ↓
build the state the declarations describe       (D)
        ↓
semantic diff M -> D
        ↓
resolve rename candidates
        ↓
safety analysis
        ↓
write the migration
```

**Nothing here reads the database.** A migration is computed from what the
models say and what the migrations already said, so two developers on one branch
get the same migration whatever database each happens to have running — and a
rename stays distinguishable from a drop and an add, because there is a history
to compare against.

```
$ orm makemigrations --name add_status

Migration 0004_users_posts

users
  ~ rename email -> email_address
  + status public.user_status NOT NULL DEFAULT 'pending'

posts
  + index posts_feed_idx
      (author_id, created_at DESC)
      WHERE status = 'published'
      INCLUDE (title)

Warnings
  W201 CREATE INDEX without CONCURRENTLY blocks writes to the table until the build finishes
      create index posts_feed_idx on public.posts

wrote migrations/0004_users_posts.json
```

With nothing to do it says so and writes nothing:

```
$ orm makemigrations
No schema changes detected.
```

### Migration IDs

`0004_add_status`: a sequence number and a name. Not a timestamp — a timestamp
makes two developers on one branch produce two migrations that both claim to be
next and sort by whose clock was ahead. A sequence makes the collision visible
instead: two migrations numbered `0004` are obviously the same position in
history, which is a conversation rather than a silent merge.

`--name` supplies the descriptive half and is sanitised to lower-case letters,
digits and underscores. Without one it is derived from the operations,
deterministically.

### Renames

The diff cannot tell a rename from a drop and an add, and the difference is
whether the data survives. So it reports candidates and asks:

```
Did you rename users.email to email_address?
    both are text, NOT NULL, with the same default. [y/N]
```

The default is no, because the destructive reading is the one already computed
and silence is not consent to rewrite it. A table rename is asked more
carefully still, and is never auto-confirmed: two tables with the same shape are
far more likely to be two tables than two spellings of one.

Without a terminal, resolve them on the command line:

```bash
orm makemigrations --rename users.email=email_address
orm makemigrations --rename-table users=accounts
orm makemigrations --no-rename          # they are not renames; drop and add
```

`--no-input` never asks. If a candidate is unresolved it fails and prints the
exact flag that would resolve it, rather than guessing in CI.

### `--check`, for CI

```bash
orm makemigrations --check
```

Loads the migrations, builds the desired schema, computes the diff, writes
nothing, touches no database, asks nothing. Exit 0 if no migration is needed,
1 if one is.

### `--dry-run`

Prints the migration and writes nothing. `--sql` also prints the statements it
would run. Repeated runs against one state produce identical output.

## `orm migrate`

```
$ orm migrate --plan
current: 0006_categories
target:  0008_feed_index

2 migration(s) to run forward:

0007_add_status [atomic]
  posts
    + status public.post_status NOT NULL DEFAULT 'draft'

0008_feed_index [non-atomic]
  posts
    + index posts_feed_idx CONCURRENTLY
      (author_id, created_at DESC)

Warnings
  W207 runs outside a transaction: an operation that fails part way through leaves the ones before it applied
      0008_feed_index
```

`--plan` is read-only, down to not creating the history table.

```
$ orm migrate
Applying 0007_add_status ... OK
Applying 0008_feed_index ... OK

2 migration(s) applied.
```

A target moves to a specific migration, forwards or backwards. It accepts a
unique prefix:

```bash
orm migrate 0007
```

A reverse plan is computed in full before anything runs, so a rollback that
would hit an irreversible operation fails without having changed anything.

### Atomic and non-atomic

A migration runs in one transaction by default, and its history row is written
inside that transaction — so either the whole migration and the record of it are
there, or neither is.

An operation PostgreSQL refuses inside a transaction block makes the migration
non-atomic, and `makemigrations` marks it so. The consequence is real and is not
hidden: an operation that fails after earlier ones succeeded leaves those
applied, and the migration is not recorded.

```
migration 0008_feed_index failed at operation 2 (create index ...) and runs
outside a transaction: the 1 operation(s) before it are still applied and the
migration is not recorded, so the database is in a state no migration describes
```

### CONCURRENTLY

```go
//orm:index posts_feed_idx (AuthorID, CreatedAt desc) concurrently
```

The index is built without blocking writes, the migration containing it becomes
non-atomic, `--plan` says so, `sqlmigrate` shows `CREATE INDEX CONCURRENTLY`,
and the executor does not open a transaction for it.

### The advisory lock

Every run takes a PostgreSQL advisory lock on one connection — the same
connection that runs the DDL and writes the history, because a lock held on a
different connection protects nothing. Two deploys migrating at once therefore
queue rather than race. If the process dies the server releases the lock.

If the lock cannot be acquired before your context expires, that is reported as
a lock that could not be acquired, not as a database that is down.

## `orm showmigrations`

```
$ orm showmigrations
[X] 0001_initial
[X] 0002_profiles
[ ] 0003_post_status
[ ] 0004_feed_index  (non-atomic)
```

A migration edited after it was applied is marked `[!]` and fails the command:

```
[!] 0004_add_status

the history and the migrations do not agree:
    0004_add_status was modified after it was applied
        applied:  9f2c1a4b7e01
        current:  33be90ad12ff

history cannot be rewritten; write a new migration instead
```

There is no flag that updates the stored checksum. History is a record of what
ran; a migration edited after the fact describes something that never happened
on any database that already has it.

## `orm sqlmigrate`

```
$ orm sqlmigrate 0004_feed_index
-- 0004_feed_index
-- runs outside a transaction: an operation that fails leaves the ones before it applied

-- create index posts_feed_idx on public.posts
CREATE INDEX CONCURRENTLY "posts_feed_idx" ON "public"."posts" ("author_id", "created_at" DESC) INCLUDE ("title") WHERE status = 'published';
```

This is exactly what the engine executes, statement for statement. The
transaction and history bookkeeping is deliberately **not** printed: it belongs
to the engine, the header says which mode applies, and printing it would produce
a script that records a migration as applied when somebody pastes it into psql
to try one statement.

`--reverse` prints the statements that would undo it.

## `orm inspect`

```bash
orm inspect          # the live schema, canonically, for a person
orm inspect --json   # the same, deterministically, for a diff
orm inspect --out schema.json
```

Read-only, in both modes. The output is normalised, so two runs against one
database produce the same bytes and the result can be committed and diffed.

## `orm check` in managed mode

Four states, reported apart:

```
$ orm check
reconciliation clean: the entities and the schema agree

Models       match the latest migration
Migrations   3 applied, none pending
Database     fully migrated, no drift
Mapping      valid
Generated    current
```

They are kept apart because "the schema does not match" is four different
problems wearing one sentence, and each has a different fix.

**Models ahead of the migrations** — write a migration:

```
Models       2 change(s) no migration describes

Models have schema changes not represented by migrations.

    table public.users column status is only in the second schema
    ...

Run:
    orm makemigrations
```

**Migrations not yet applied** — run them:

```
Migrations   1 applied, 2 pending
Database     behind the migrations

Pending migrations:

    0007_add_status
    0008_feed_index

Run:
    orm migrate
```

**The database changed behind the migrations** — this is drift, and only this:

```
Database     drift: 1 difference(s) from the applied migrations

Database drift detected.

The applied migrations describe a schema the database does not have. Something
changed it outside the migrations; nothing here will quietly rewrite the
migration state to match.

    table public.users column status is only in the first schema

Either undo the change, or write a migration that describes it and record it with
    orm migrate --fake <migration>
```

Drift is computed against the state as of the **last applied** migration, not
the latest one. Reporting an unrun migration as drift would train people to
ignore drift — and the repair for drift is to change the database by hand, which
is what caused the drift the tool actually means.

`Generated` is a separate line for the same reason: a stale migration and stale
generated code are different problems. Having never generated is reported and
does not fail unless you ask with `--generated`, because the workflow this tool
recommends runs `check` before the first `generate`.

### In database mode

Nothing changes. A database-first project has no migrations to report on and
must not start failing because it has none; the migration commands refuse
politely and `orm check` behaves exactly as it did.

## `orm generate` in managed mode

Generation reads the live database, because that is where the mapping it proves
has to hold. So in managed mode it refuses unless the three states agree:

```
orm generate: schema changes are not represented by migrations; run orm makemigrations
orm generate: the database is behind the migrations; run orm migrate
orm generate: the database differs from what its applied migrations describe, ...
```

Generating from a database no migration explains would bake an unreviewed schema
into the runtime types — code that compiles, passes its own check, and describes
something nobody approved.

## Adopting an existing database

A database-first project becomes a managed one without recreating anything.

```bash
orm inspect                      # look at what you have
orm makemigrations --baseline    # write the migration that describes it

# read it, commit it, then set schema.mode: managed in orm.yaml

orm migrate --fake 0001_initial  # record it as applied, running nothing
```

`--baseline` is the one migration command a database-first project may run,
because it changes nothing: it reads the schema you already have and writes a
file. Everything after it needs `mode: managed`, which is the point at which you
have decided who owns the schema.

`--baseline` is the one place a migration is computed from a live database, and
it is the right answer there: the question is not "what should the schema be"
but "what is it already", so that everything after this point is an increment.

`--fake` verifies before it records. It reads the live schema, compares it with
the state the migration describes, and refuses if they differ:

```
orm migrate: the database is not in the state 0001_initial describes, so recording
it as applied would make the history claim something untrue:

    table public.users column status is only in the first schema

run the migrations instead, or pass --force if you are certain the difference
does not matter
```

Nothing is ever faked automatically. Recording a migration as done when it was
not is a claim about a database that only the person making it can justify.

## Data migrations and raw SQL

The generated diff describes schema, not data. When a change needs data moved,
edit the migration.

**`raw_sql`** runs SQL the engine does not model:

```json
{
  "op": "raw_sql",
  "args": {
    "Up": "UPDATE users SET status = 'active' WHERE status IS NULL",
    "Down": "",
    "Atomic": true,
    "Description": "backfill status"
  }
}
```

Nothing parses it. If your raw SQL **changes the schema**, the migration state
will not know unless you say so — pair it with a `state_only` operation that
describes the change without running anything:

```json
{ "op": "state_only", "args": { "op": "drop_column", "args": { "Schema": "public", "Table": "users", "Name": "legacy" } } }
```

Together they are how a hand-written migration keeps the state honest without
the engine having to understand SQL. Leaving the pair out means the next
`makemigrations` will propose to make the change again, and `orm check` will
report drift — which is the system telling the truth.

**A data migration written in Go** (`migrate.RunFunc`) is available to a program
that builds its own `migrate.Set`, and deliberately cannot be written to a
migration file: a function has no representation there, and the command-line
tool could not resolve one. It receives a narrow SQL runner rather than the
generated API, because a migration written today has to keep working after the
entity it was written against is renamed or deleted.

## Safety

Every operation carries an advisory classification, and warnings carry stable
codes:

| code | |
|---|---|
| `W201` | `CREATE INDEX` without `CONCURRENTLY` blocks writes while it builds |
| `W202` | `DROP COLUMN` discards the column's data |
| `W203` | `DROP TABLE` discards the table and everything in it |
| `W204` | `SET NOT NULL` scans every row and fails if any is NULL |
| `W205` | a type change may rewrite the whole table under an exclusive lock |
| `W206` | dropping a constraint or index discards what it guaranteed |
| `W207` | the migration runs outside a transaction |
| `W208` | a `NOT NULL` column with no default cannot be added to a table with rows |
| `W209` | the constraint is validated against every existing row under a lock |
| `W210` | the operation cannot be reversed |
| `W211` | raw SQL runs as written and is not modelled |

Warnings are never errors. The classification describes what an operation does
to a table, not what that means for your deployment: whether a lock matters
depends on your traffic, and whether dropping a column loses anything depends on
what is in it. A tool that refused to run a migration because dropping a column
is destructive would be a tool nobody could use to drop a column.

### The two changes that are refused

**A `NOT NULL` column with no default.** PostgreSQL has nothing to put in
existing rows, and nothing here knows whether your table is empty. Add it
nullable, backfill, then make it `NOT NULL` — three steps, in two or three
migrations, which is the shape that works on a table with rows in it.

**Removing an enum label.** PostgreSQL cannot remove one. The type would have to
be rebuilt, which needs every row still holding the value to be given another
value first — a data migration whose correct form depends entirely on what your
application means by the value being removed. `makemigrations` refuses and says
so rather than generating a drop-and-recreate that would guess about data.

### Production patterns PostgreSQL gives you

Adding a validated constraint locks the table while it checks every row. The
staged form does not:

```
ALTER TABLE ... ADD CONSTRAINT ... NOT VALID;   -- takes no long lock
ALTER TABLE ... VALIDATE CONSTRAINT ...;        -- scans without blocking writes
```

The canonical model represents `NOT VALID` and the diff turns "was not valid,
now expected valid" into a `VALIDATE CONSTRAINT` rather than a rebuild. In a
generated migration, split the constraint into two migrations by hand.

## CI

```yaml
- run: orm makemigrations --check    # a declaration with no migration fails the build
- run: orm check                     # models, migrations, database, mapping, generated
- run: go test ./...
```

Migration rendering and checksums are deterministic, so a regenerated migration
is byte-identical to the committed one, and a repeated `makemigrations --dry-run`
against one state produces the same operations every time.
